# Установка orgBox: BaseShop на 1С-Битрикс

Состояние реализованных функций и план до сдачи: [ROADMAP.md](ROADMAP.md).

## Требования

- актуальная поддерживаемая версия 1С-Битрикс;
- PHP 8.1+;
- модули `main` и `iblock`;
- каталог проекта развёрнут как document root сайта;
- в настройках веб-сервера `index.php` должен иметь приоритет над сохранённым статическим `index.html`.

Модули `sale` и `catalog` не используются.

## Быстрый запуск

1. Скопируйте файлы репозитория в корень сайта с установленным Bitrix. Каталог `/bitrix/` не заменяйте. Если на сайте уже есть `urlrewrite.php`, добавьте в него правило из репозитория вместо замены всего файла.
2. Авторизуйтесь под администратором.
3. Откройте `/local/tools/orgbox_baseshop_setup.php`.
4. Укажите email менеджера, при необходимости телефон и запустите настройку.
5. Проверьте, что сайту назначен шаблон `orgbox_baseshop`.
6. В административной части откройте **Контент → orgBox: BaseShop → Товары** или **Баннеры на главной**. Три демонстрационных баннера создаются при первом запуске настройки; ими можно управлять и из публичного режима правки.
7. Остальные тексты главной и логотип редактируются в публичном режиме Bitrix как включаемые области из `/include/orgbox_baseshop/`: блоки главной — в `home/`, а в `logo/` находятся текст до знака, сам знак и текст после него.
8. Очистите управляемый кеш после изменения структуры или настроек.

Setup создаёт инфоблоки товаров и заказов, свойства, почтовое событие и шаблон письма. Его можно запускать повторно.

## Импорт исходного каталога

После первоначальной настройки откройте под администратором `/local/tools/orgbox_baseshop_import_catalog.php`. Импортёр создаёт разделы и загружает все товары из `/local/js/catalog-data.js` вместе с изображениями из `/local/assets/catalog-products/`.

- существующие товары определяются по артикулу и обновляются без дублей;
- URL товаров имеют нейтральный вид `/catalog/{section}/product-{article}/`;
- внешние ссылки и названия сторонних площадок не импортируются;
- демонстрационный товар можно удалить автоматически;
- повторную загрузку изображений следует включать только после изменения файлов;
- поскольку исходные данные не содержат веса и размеров, перед запуском задайте значения упаковки по умолчанию, а затем уточните их в административной части.

## Поля товара

Стандартные поля: `NAME`, `CODE`, `ACTIVE`, `PREVIEW_TEXT`, `DETAIL_TEXT`, `PREVIEW_PICTURE`, `DETAIL_PICTURE`.

Свойства: `PRICE`, `ARTICLE`, `WEIGHT`, `LENGTH`, `WIDTH`, `HEIGHT`, а также необязательные `OLD_PRICE`, `GALLERY`, `BADGE`.

Цена хранится числовым свойством инфоблока. Разделы инфоблока являются категориями каталога.

## Настройки и секреты

Приоритет настроек:

1. переменная окружения `ORGBOX_BASESHOP_<KEY>`;
2. Bitrix option решения `orgbox.baseshop`;
3. `local/php_interface/orgbox_baseshop/config.local.php`;
4. безопасное значение по умолчанию.

Для локального файла скопируйте `config.local.php.example` в `config.local.php`. Целевой файл игнорируется Git.

Параметр `theme` выбирает CSS-пресет из `/local/css/themes/`. В поставку входит пресет `dark`. Цвета и шрифты задаются семантическими переменными `--theme-*`, поэтому новый клиентский дизайн не требует переименования шаблона или компонентов.

## Именование решения

Товарный знак в интерфейсе и документации пишется как `orgBox`. В PHP используется техническое написание `OrgBox`. Машинные идентификаторы следуют требованиям и соглашениям платформы: шаблон `orgbox_baseshop`, компоненты `orgbox:*`, option ID `orgbox.baseshop`.

## Доставка: первый этап — СДЭК

В оформлении доступны СДЭК курьером, СДЭК в ПВЗ, Почта России и Яндекс Доставка в ПВЗ. Рассчитывается только выбранный вариант. Почта рассчитывает базовую посылку до отделения по индексу. Яндекс требует отдельной настройки, описанной ниже. Условные цены не используются.

СДЭК использует API v2: OAuth `POST /oauth/token`, затем `POST /calculator/tariff`. Первый поддержанный тариф — **137, склад — дверь**: отправитель сдаёт посылку в СДЭК, получателю доставляет курьер. Выбор ПВЗ с тарифом 136 описан ниже. Создание накладных не реализовано. Используется `total_sum` из ответа API, а не локальная формула.

На сервере задайте в `config.local.php`, окружении или Bitrix options:

- `cdek_client_id` / `ORGBOX_BASESHOP_CDEK_CLIENT_ID`;
- `cdek_client_secret` / `ORGBOX_BASESHOP_CDEK_CLIENT_SECRET`;
- `cdek_origin_code` / `ORGBOX_BASESHOP_CDEK_ORIGIN_CODE` — код города отправления из справочника СДЭК, не почтовый индекс;
- `cdek_sandbox` / `ORGBOX_BASESHOP_CDEK_SANDBOX` — `false` для рабочего API, `true` для тестового API. Тестовая среда проверяет вызов, но не разрешает оформление заказа по тестовой цене.

Ключи не передаются в браузер и не записываются в Git. Пустые настройки, ошибка API, неполный ответ и незаполненные размеры блокируют оформление; условного fallback-тарифа нет. Для всех товаров укажите вес в граммах и размеры упакованного товара в сантиметрах. Для нескольких одинаковых товаров используется одна упаковка: вес и высота умножаются на количество, длина и ширина остаются прежними. Это допущение требует проверки на реальных упаковках.

После изменения количества, города, индекса, адреса или службы результат сбрасывается. При отправке сервер заново рассчитывает тариф и требует пересчёт, если стоимость изменилась. Сумма в браузере служит проверкой изменения, итог заказа определяется сервером.

Проверка интеграции на установленном Bitrix: настроить рабочие ключи и город отправления, выбрать товар с проверенной упаковкой, рассчитать несколько направлений, сверить тариф с кабинетом СДЭК, оформить тестовый заказ. Без этих настроек реальный расчёт не запускается.

Документация API: https://apidoc.cdek.ru/.

## Маршруты

- `/` — лендинг;
- `/catalog/` — весь каталог;
- `/catalog/{section}/` — раздел;
- `/catalog/{section}/{product}/` — карточка товара;
- `/order/?product={id}` — отдельная страница оформления заказа;
- `/local/ajax/orgbox-baseshop-checkout.php` — POST-only AJAX с проверкой Bitrix sessid.

## Проверка заказа

1. Откройте товар и нажмите «Купить».
2. Заполните получателя, город, индекс и адрес.
3. Рассчитайте и выберите доставку.
4. Отправьте заказ.
5. Убедитесь, что элемент появился в инфоблоке «Заказы» со статусом `NEW`.
6. Проверьте очередь/журнал почтовых событий и доставку письма менеджеру.

Сервер повторно получает цену и параметры товара из инфоблока, пересчитывает доставку и итог. Значения цены из JavaScript не принимаются.

## Ограничения v0.1

- один заказ содержит один вид товара;
- нет регистрации, корзины, оплаты, остатков и SKU;
- СДЭК и Яндекс требуют настройки и проверки рабочих credentials; Почта России использует публичный тарифный API, индекс отправления настраивается;
- интеграция Bitrix24 предусмотрена интерфейсом уведомлений и может быть добавлена отдельным exporter без изменения checkout;
- тексты секций лендинга редактируются как включаемые области; сложного визуального конструктора в v0.1 нет.

## Яндекс Доставка: доставка в ПВЗ

Третий пункт теперь — **Яндекс Доставка** (`yandex`). Используется API «Доставка по России», не API экспресс-курьеров. В этой ветке реализована доставка до ПВЗ; СДЭК поддерживает курьера до двери и выбор ПВЗ, описанный ниже. Почта России поддерживает расчёт до отделения по индексу, описанный ниже.

Город отправления магазина — **Тольятти**. На сервере задайте:

- `yandex_token` / `ORGBOX_BASESHOP_YANDEX_TOKEN` — Bearer-токен из профиля кабинета Яндекс Доставки;
- `yandex_origin_station_id` / `ORGBOX_BASESHOP_YANDEX_ORIGIN_STATION_ID` — ID склада отправки в Тольятти, зарегистрированного в платформе (получить у менеджера Яндекса); название города не заменяет этот ID;
- `yandex_sandbox` / `ORGBOX_BASESHOP_YANDEX_SANDBOX` — `false` для рабочего API, `true` для тестового контура.

Токен хранится только на сервере. Без настроек список ПВЗ и расчёт недоступны; условные тарифы не используются. Тестовый контур не позволяет оформить заказ по тестовой цене.

Покупатель выбирает Яндекс, вводит город и нажимает «Найти ПВЗ». Если Яндекс возвращает несколько населённых пунктов, нужно уточнить город и область. Список показывает адреса; после выбора — часы работы по местному времени ПВЗ. Карта, постаматы и курьер Яндекса в этот этап не входят.

Используются `POST /api/b2b/platform/location/detect`, `/pickup-points/list` и `/pricing-calculator` с тарифом `self_pickup`. Вес — граммы, габариты — сантиметры, оценочная стоимость — копейки. `pricing_total` возвращается строкой с валютой `RUB`, а `delivery_days` — числом дней. Сохраняется предварительный тариф API, стоимость повторно проверяется при заказе. Предположение об одной общей упаковке нескольких одинаковых товаров сохраняется и требует проверки.

Смена города/службы очищает выбранный ПВЗ; смена количества/ПВЗ сбрасывает цену. Сервер проверяет выбранный ID по актуальному списку этого города и сохраняет подтверждённый API адрес и ID ПВЗ в существующем поле `ADDRESS` заказа. Индекс берётся из ПВЗ; домашний адрес для Яндекса не требуется. Данные ПВЗ из браузера не используются как адрес заказа, новые свойства инфоблока не требуются.

Калькулятор использует `already_paid` и `client_price=0` только для оценки; сайт не принимает оплату и не создаёт/подтверждает отправление в Яндексе. Менеджер согласует оплату и создаёт отправление отдельно. Перед запуском сверить тариф с кабинетом, проверить реальные ограничения упаковки и оформить тестовый заказ на установленном Битриксе.

Официальные контракты:

- https://yandex.ru/support/delivery-profile/ru/api/other-day/
- https://yandex.ru/support/delivery-profile/ru/api/other-day/ref/2.-Tochki-samoprivoza-i-PVZ/apib2bplatformlocationdetect-post
- https://yandex.ru/support/delivery-profile/ru/api/other-day/ref/2.-Tochki-samoprivoza-i-PVZ/apib2bplatformpickup-pointslist-post
- https://yandex.ru/support/delivery-profile/ru/api/other-day/ref/1.-Podgotovka-zayavki/apib2bplatformpricing-calculator-post


## Почта России: базовая посылка в отделение

Настройка `russian_post_origin_postal_code` задаёт индекс отправления. Исходное значение — `445027` (Тольятти). Меняйте его в `public_html/local/php_interface/orgbox_baseshop/config.local.php` либо через `ORGBOX_BASESHOP_RUSSIAN_POST_ORIGIN_POSTAL_CODE`; править код провайдера не требуется. Переменная окружения имеет приоритет над настройкой модуля Bitrix и локальным конфигом. Индекс отправления не принимается из браузера.

Используется публичный API v2 `https://tariff.pochta.ru/v2/calculate/tariff/delivery`, объект `4030` (базовая посылка в своей упаковке). Токен и ключ API «Отправка» для этого калькулятора не нужны; существующие поля зарезервированы. Стоимость `paynds` включает НДС и переводится из копеек в рубли, срок — нормативный диапазон `delivery.min/max`, не гарантия даты. Договорные скидки не учитываются.

Покупатель указывает город, шестизначный индекс отделения получения и адрес получателя. Упаковка должна иметь адресную сторону не меньше 24 × 16 см; поддерживаются вес до 10 кг, стороны до 60 см и сумма сторон до 120 см. Вес передаётся в граммах, размеры округляются вверх до целых сантиметров. Для количества больше одного сохраняется общее допущение упаковки (вес и высота умножаются на количество); проверить реальные размеры обязательно.

Нет объявленной ценности, наложенного платежа, создания отправлений и печати ярлыков. Ошибки API, отсутствующая стоимость/срок или неподдерживаемая упаковка блокируют заказ без условной цены. Перед сохранением заказа тариф рассчитывается повторно; изменившаяся цена требует пересчёта.

Проверки с ответами по контракту API выполняются локально. Живой запрос из среды разработки получил блокировку HTTP 417; перед выпуском проверить расчёт с сервера магазина, сверить с калькулятором Почты и оформить тестовый заказ на Битриксе.

Официальные источники: https://tariff.pochta.ru/post-calculator-api.pdf и https://info.pochta.ru/support/parcels/parcel.


## Единый раздел админки «Оргбокс»

После установки изменений у администратора появляется отдельная кнопка «Оргбокс» внизу левой панели. В ней два независимых пункта:

- **Настройки**: название магазина, телефон, email уведомлений о заказах, город отправления, существующая тема оформления и ID инфоблоков (0 — автоматическое определение).
- **Настройки доставки**: ключи и код города СДЭК, токен и ID станции Яндекса, тестовые режимы, индекс отделения отправления Почты России.

Прямые адреса: `/local/admin/orgbox_baseshop_settings.php?section=general` и `?section=delivery`. Раздел подключён обработчиком административного меню из `local/php_interface/init.php`; новый модуль устанавливать и ядро Bitrix менять не требуется. Новые пункты можно добавлять в `Admin/ShopSettings::menu()`.

Настройки сохраняются в `Bitrix\Main\Config\Option` модуля `orgbox.baseshop` и имеют приоритет над локальным конфигом. Переменные окружения остаются приоритетными; такие поля показаны как заблокированные с именем переменной, изменить их можно только на сервере. Данные локального конфига продолжают работать до первого сохранения соответствующего раздела. Пустые строки, явно сохранённые в админке, переопределяют прежние значения конфига.

Сохранённые ключи не выводятся в HTML: отображается только «Ключ задан»/«Ключ не задан». Пустое поле сохраняет старый ключ, заполненное заменяет его, отдельная галочка удаляет. Доступ — только администратору, POST требует Bitrix sessid. Поля другого раздела не сохраняются.

Локальные проверки охватывают чтение и сохранение, ключи, проверку полей, права и CSRF, HTML формы и структуру меню. Фактическое положение кнопки и работу сохранения на установленном Bitrix нужно проверить после выкладки; Bitrix в среде разработки отсутствует.


## СДЭК: выбор пункта выдачи

Добавлен вариант «СДЭК — в пункт выдачи» (`cdek_pickup`), курьер (`cdek`, тариф 137) сохраняется. Оба варианта используют общие настройки из «Оргбокс → Настройки доставки»: client_id, client_secret, код города отправления и тестовый режим. Отдельные ключи для ПВЗ не нужны.

Покупатель вводит город, нажимает «Найти ПВЗ», выбирает пункт из списка с адресом и графиком работы, затем рассчитывает доставку. При неоднозначном городе нужно указать область через запятую, например «Самара, Самарская область». Индекс и домашний адрес для ПВЗ не требуются. Смена города/службы очищает пункт; смена количества/пункта сбрасывает цену. Запоздалые ответы не восстанавливают старый выбор, в том числе при переключении между СДЭК и Яндексом.

Используются GET `/v2/location/cities` и `/v2/deliverypoints` с фильтрами города, RU, PVZ и выдачи. Список загружается постранично, закрытые пункты исключены; постаматы в этот этап не входят. При расчёте сервер повторно запрашивает выбранный код, проверяет город, статус ACTIVE, выдачу, адрес и ограничения веса/габаритов с учётом поворота посылки. Вес упаковки — граммы, ограничения офиса — килограммы; размеры округляются вверх в сантиметрах. Отсутствующее ограничение не трактуется как ноль.

POST `/v2/calculator/tariff` использует тариф 136 «склад — склад», `delivery_point` выбранного пункта и подтверждённую сервером локацию. По официальному контракту калькулятор может подменять неподходящий офис; все предупреждения расчёта ПВЗ блокируют оформление. Тариф и пункт повторно проверяются при заказе, браузерный адрес/индекс/цена не определяют сохранённые данные. Официальный адрес и код сохраняются в существующем ADDRESS, индекс — из ПВЗ, служба — «СДЭК: в ПВЗ». Новые свойства инфоблока не требуются.

Срок API указан в рабочих днях, стоимость — `total_sum` с НДС и услугами. Это расчёт, а не создание накладной. Общая модель одной упаковки для количества сохраняется и требует проверки реальной упаковки.

Проверено локально на ответах по контракту: список, статус, неоднозначные города, подмена и исчезновение пункта, ограничения, предупреждения, цена, сохранение заказа и смена службы. Живые вызовы и тестовый заказ в Bitrix требуют рабочих ключей СДЭК и корректного кода Тольятти; без настроек расчёт и ПВЗ недоступны.

Официальный контракт: https://apidoc.cdek.ru/ и опубликованная этим порталом спецификация https://gateway.cdek.ru/api-cdek-docs/web/docs/merged?sectionId=api_v2_integration.
